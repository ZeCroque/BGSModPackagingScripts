# Package Scripts for BGS mods

A bunch of scripts I use to prepare releases for my Starfield/Fallout 4/Skyrim mods, both for the Creations store and NexusMods.

## Prerequisite files

To work properly the scripts needs the following:
- A `preset.json` file containing a root object with the following fields:
    - `modName`: The name of the mod that will be used for the mod filename, etc...
    - `modShortName`: A 3-letters abbreviation which will be used as a prefix for the editor Ids, will be the root namespace for the scripts and will prefix the achlists and the thumbnail files.
    - `modVersion`: The version that will be used by the FOMOD if any.
    - `buildCode`: An integer that will be used by the `modShortName:Utility:ModInfo:GetModVersion()` function which is meant to be used by the mod updating logic.
    - `modSize`: Should be `Small`, `Mid` or `Full`. Will be used to automatically convert the `.esp` to the `.esl` format if appropriate (and hopefully for Starfield at some point).
    - `game`: Should be either `Starfield`, `Fallout4` or `Skyrim`.
    - `gamePath`: The game path.
    - `mo2Path`: The path to the folder containing MO2's exe file.
    - `mo2InstanceName`: The name of the instance handling the modded game.
- A `ModPage/readme.md` file with custom formatting that can be parsed into a regular .md file by the `readme_formatter.py` script (see below).
- A `Data/modShortName_Main.achlist` that will be used to create the mod archives.
- A `Data/modName.esp` file, obviously
- A `modNameDebug.ppj` file and a `modNameRelease.ppj` file

All of these files are automatically generated by using my [modding project template](https://github.com/ZeCroque/BGSModProjectTemplate).

## Optional files

You can also add the following files for extra functionnality:
- A `FOMOD` folder for the nexus archive.
- A `modShortName_Thumbnail.png` that will be used by the FOMOD if applicable.
- A `Data/modShortName_Voices.achlist` that lists the plain vanilla voice file to ship.
- A `Data/modShortName_ModdedVoices.achlist` that lists the spliced/AI generated voices that won't be added to the Creations archive but will be added to the Nexus release. A special Bethesda archive suffixed by `_NO_AI` is also generated without those files, it's meant to be used by the FOMOD.
- Several `Data\LocalizedVoices\languageCode` folders containing the localized voices to create localized archives for the Nexus release. Supported language codes can be found in the `GetAvailableLanguagesSuffixes` function of the `utils.py` script.
- A `creationsModpageSections.json` containing a table listing the name, in capital letter, of the readme sections to keep for the Creations modpage. By default, the "OVERVIEW" and "DETAILS" sections are already included (see below for more info).

## Additional requirements

The localization and the SEQ generation logics requires to have a MO2 profile called `ZZZ_modName`, which preferably has activated your WIP mod (you can make a junction to this repository's `Data` folder instead of copy/pasting) and redirects the managed targets' output to this folder instead of the overwrite. It also needs to have the following targets: `xTranslator` and `Creation Kit`.

## Localization process

The localization process is quite long and will launch the Creation Kit several times. It is the official BGS process. It requires some preparation as seen in the previous section. For Starfield, if you are releasing a small/mid master, the CK will fully launch after automatically/opening closing 3 times. When that happens, you need to load your mod and convert to the appropriate format, and then close the window and the process will continue.

Note that the changes made to the `.esp` by this process should never be saved for future development, so either backup the file before localizing or discard the changes if you're using a versionning system.

At the end of the official BGS procedure, xTranslator will be started to translate the generated string files. If you're running the full packaging logic, it allows you to translate before starting archives creation.

## Readme formatting

The readme file inside the `ModPage` folder must respect the following structure:
- A title at the first line with the greatest heading (one "#"), which will only appear in the "nexus" output
- An index starting with `## Index` right after
- Optionally some "header content" before the first section (not appearing in the "Discord" output)
- A `## 1. OVERVIEW` section and a `## 2. DETAILS` section right after
- And finally any number of section starting by `## X. SECTION NAME`

The `readme_formatter.py` script will outputs several files inside the `./output` folder to go on every handled platforms (it will also replace the `readme.md` file at root with a "copier" badge at the top, if applicable, followed by the "readme" output). Here's a sum up of those outputs:
- The "nexus" output will basically be the full readme, without the index, with all markdown markings converted to Nexusmods' proprietary BBCode tags.
- The "creations" output, due to character limitations, will be a simplified version containing the header, the `OVERVIEW` and `DETAILS` sections and then all sections listed in the optional `creationsModpageSections.json` file. All titles will be made one tier higher because the main title is not kept (so "##" becomes "#"). All links will be removed since there are not supported. Finally, if a footer delimited by `CREATIONS_FOOTER` and `CREATIONS_FOOTER_END` is present in the file, it will be appended as a final section with the appropriate section number.
- The "creations_af" output, is the same as above but with some additional special marking handling (see below).
- The "readme" output will be the full readme, keeping the special markings of the Nexus variant and nothing else. Meant to be in the nexus archive.
- The "discord" output will keep the special markings of the Nexus variant and then will split the readme based on its sections and make a convenient copy/pastable base to post in several topics of your Discord server.

Eventually, as it has been mentionned before, there is custom marking to make certain portions of the readme only available on specific platforms. Here's a list:
- `@My Text@`: everything between the `@` will only be present in the "nexus", "readme" and "discord" outputs
- `|My Text|`: everything between the `|` will only be present in the "creations" and "creations_af" output
- `<My Text>`: everything between `<` and `>` will only be present in the "creations_af" output
